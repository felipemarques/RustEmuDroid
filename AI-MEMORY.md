## Architecture

| Decision | Consequence for future work |
|---|---|
| The Rust desktop client uses eframe/egui and Glow. Android Home is a native Android activity inside the guest. | Games, apps and Home navigation share one Android session. Host controls and preferences belong to the desktop window. |
| The native runtime uses the Android Emulator controller and ADB. The Windows Kemu engine can provide its matching Android image and graphics stack. | A different hypervisor or disk format alone does not supply the controller, guest drivers or display/input protocol the embedded UI uses. |
| Each Android profile owns its writable storage. | Check the profile before attributing missing games, different Android versions or different GPU settings to a regression. |
| Home is bundled in the executable as a signed APK. | Rebuild the APK when changing Home sources or resources. Preserve the signing key when upgrading a profile in place. |
| New desktop installations default to pt-BR. The client also supports en-US and es-ES. | Store the selected locale with the launcher preferences and apply it to the bundled Home; third-party apps manage their own language. |
| The sidebar keyboard opens the quick controls menu. The editor floats over the fitted guest image. | Anchor markers to normalized Android coordinates. Cover the game with an egui foreground area when editing so a panel or letterbox never becomes a touch target. Existing schemes remain in the AVD's `touch-maps.json`. |

## Verification history

- On Windows v0.8.1, `doctor` confirmed WHPX and `init` created the Google Play API 37.0 profile with `--sdk` pointed at a temporary root exposing only the emulator, platform-tools and one system image via directory junctions. Android environment variables pointed to the test root and PATH contained only Windows system directories. This checked discovery and profile creation on a machine with the packages already installed. A clean-machine boot and game FPS with a packaged runtime remain untested. [Runtime prerequisites](README.md#prepare-the-android-runtime)

- On Windows v0.8.0, the unmodified API 28 revision 4 SDK control reached Android boot in 29.5 seconds with SELinux enforcing, Launcher3, multitouch and RTX 5070 Ti-backed guest GLES. R1 combined SDK system-as-root board inputs with the copied Pie64 framework and 47 factory APKs. All 4,151 staged paths were verified offline. R1 exposed the expected ADB console transport, but its guest shell repeatedly returned `error: closed` and the run ended after 183.83 seconds without confirmed boot. A separate SDK kernel/logcat run recorded R1 guest SurfaceFlinger initializing RTX-backed OpenGL ES and caching 24 shaders. It also found that `vold` looked for absent `/fstab.pie` during userdata setup. R2 adds the official board fstab at that path with forced encryption preserved. Its first diagnostic used a 1 MiB userdata seed without a valid ext4 superblock, so it could not isolate the fstab change. With a formatted 6 GiB seed, R2 mounted encrypted userdata and reached Zygote, then logged enforcing SELinux denials from `system_server` still in the Zygote domain and an ensuing dexopt exception. ADB shell and completed boot remained unconfirmed. [R1 assembly, hashes and commands](docs/bluestacks-lab.md#cold-boot-the-goldfish-system-as-root-candidate)

- On Windows v0.8.0, the Android EGL multifile cache and a 128 MiB cache limit both left the PUBG first-close Inventory pause in place. During the longest measured gaps, QEMU's RTX 5070 Ti 3D engine was active 0.70% with the 128 MiB limit and 0.00% with the original settings. Both guest overrides were restored. [Game and host measurements](docs/game-testing.md#egl-shader-cache-and-host-gpu-activity-during-inventory)

- An offline Android 9 VINTF check found that the Goldfish device matrix requires a Vendor NDK 28 declaration absent from the Pie64 framework. The original r61 full-tree CLI can exit with success after logging an incompatibility. Use the direction-specific pairwise result as well. The populated Pie64 data filesystem separately passed all five read-only fsck passes. [Board compatibility](docs/bluestacks-lab.md#could-the-android-9-sdk-supply-the-missing-drivers) · [Populated data](docs/bluestacks-lab.md#populated-data-disk)

- On Windows with Android 17, the rolling replay test decoded a 720 × 405 JPEG XL with 30 frames spaced 100 ms apart. Its first frames showed Android Home, its last frames showed Settings, and Quick Settings opened after the save shortcut was absent. Replay starts off and requires three seconds of continuous sampling after arming or resetting. [Live shortcut and clip check](src/ui/rolling_replay_test.rs)

- On Windows v0.7.0, PUBG's Lobby Adaptive Graphics setting did not resolve the Inventory stalls. All three 48-second runs paused for over a second after the first close. The original settings were restored. [Adaptive Graphics comparison](docs/game-testing.md#does-disabling-adaptive-graphics-help-inventory)

- The Linux v0.7.0 release booted Android 17 Google Play under WSLg and KVM, with the bundled Home as default. On Ubuntu 24.04 the selected Mesa D3D12 driver exposed the Radeon 780M to native GLES. BombSquad presented 60.00 frames/s in Death Match with its per-app driver set to `native`. The default ANGLE path presented 29.81/s in King of the Hill using CPU Vulkan. The random scenes differed. The test restored the original per-app settings. [Boot times, driver selection and game data](docs/linux-runtime.md)

- Game schemes store independent X/Y multipliers for relative mouse movement in aim and free look. Legacy schemes use 1.00 on each axis. With X 2.00 and Y 0.50, equal raw mouse deltas produced the expected asymmetric contact on the Android 17 touchscreen and focus loss released it. The quick menu's device choice filters the visible hints. A D-pad can combine its direction keys with either analog stick.

- The 0.6.1 desktop path uses the same decoded bytes for capture and OpenGL texture upload on GL/GLES 3+. In a Windows A/B test with the same live Unity scene, mean CPU preparation per frame fell from 1.22 to 0.21 ms. The native desktop panel used the Radeon 780M while the game used the RTX 5070 Ti. [Measurements](benchmarks/desktop-texture-upload/README.md)

- On the Windows Radeon 780M with SDK 37.3.10, use the guest's Vulkan memory types to check which heaps are CPU-visible. The original configuration exposed only 256 MiB to CPU-visible allocations. Disabling the SDK's device-memory-only policy for the selected session also exposed a 16,240 MiB heap. FPS WW2 URP then entered Level 1 on native Vulkan with Max quality and Very High antialiasing. The opt-in preference belongs to the Android profile. [Measurements and memory-type evidence](docs/game-testing.md#radeon-780m-vulkan-compatibility)

- On Windows, the SDK could block before ADB on a crash-report dialog after a previous VM failure. In 0.4.1 the SDK logged its reporter disabled and Android 17 booted in 23.5 s embedded and 24.6 s headless. The retained session log and Android boot property cover these two paths. The embedded SuperTuxKart replay averaged 60.02 game FPS at the 60 FPS cap across two runs. [Replay settings](docs/game-testing.md#supertuxkart-release-comparison)
- The stock Pie64 kernel mounted the verified factory data seed read-only at `/data` via VirtIO SCSI. In separate diskless display probes the kernel bound the VirtIO PCI transport without a GPU driver; standard VGA provided a VESA framebuffer, and neither device exposed the DRM card used by the supplied composer. Check these storage and display milestones separately from the vendor's early configuration failure. [Pie64 device checks](docs/bluestacks-lab.md#display-hardware-available-to-the-copied-kernel)
