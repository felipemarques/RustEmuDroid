# RustEmuDroid v0.24.0

The Windows performance engine can now let the Windows hypervisor emulate each virtual CPU's local interrupt controller (xAPIC) instead of the engine's own user-mode copy. Engines whose manifest lists the new capability `whpx_apic_hv` get it as part of the existing **CPU virtualization tuning** switch in **Settings → Runtime, image, and profile → Performance engine (experimental)**; there is no separate switch. Turning the switch off also turns this off. [Build the engine](../../experiments/whpx-clock/README.md#4-build-the-performance-engine)

When the hypervisor emulates the interrupt controller, the local APIC fast path and the paravirtualized end of interrupt from v0.23.0 no longer apply, and the guest no longer reports KVM as its hypervisor. If the host's hypervisor cannot provide this mode, the engine keeps its user-mode controller with those two options and Android starts normally; the startup status names the reason the engine gave. The engine prints `RustEmuDroid QA: WHPX local APIC emulated by the hypervisor (xAPIC)` when the mode is active.

On the Windows test PC (RTX 5070 Ti, official Android 17 Google Play image, SuperTuxKart 1.5 Black Forest at High, Vulkan Mailbox uncapped, Best performance power mode, during the day with other desktop programs using about 0.8 host core), one interleaved series on the same engine binary measured **345.2 game FPS** with the user-mode controller and **380.1** with the hypervisor, with no lap below 372. Two later boots measured 378–392. VM exits that reached the engine during the race fell from about 20,000 to 5,500 per second. BlueStacks measured 427.5 in the same daytime condition, so the gap in that mode narrowed from 22–25% to about 12%. Balanced mode and an idle desktop have not been measured with this option yet. In a later daytime series with the release executable, the v0.24.0 client applying these settings from its preferences measured 367.2 FPS on three ordinary laps against 379.1 for the test operator applying them by hand, with the same options confirmed in the engine log; with four laps per arm and one slow 287.5 lap in the client arm, that series does not show the two paths to be equal in speed. [Measurements and analysis](../../docs/performance-history.md#hypervisor-local-apic)

The analysis in the same report finds that most of the remaining difference in this game follows the Android image's memory allocator rather than the engine: pure computation runs at the same speed in both guests, while SuperTuxKart's many small heap objects are placed less contiguously by Android 17's allocator than by BlueStacks' Android 9 one. [Where BlueStacks is faster](../../docs/performance-history.md#where-bluestacks-is-faster)

The client now confirms the shared graphics transport from the engine's own consumer line only, because the emulator's `androidboot.hardware.gltransport=asg` line can be split in the log by another writer, as seen once in a test run.

Unchanged: the other switches, the manifest format (one new capability name; older clients ignore it), the `config.ini` handling, the power mode option and the default engine. Engines without `whpx_apic_hv` behave exactly as in v0.23.0. On the integrated Radeon 780M at 60 Hz, Cipó Livre stayed at the 60 Hz cap with both controllers (59.97–60.00 presentations/s with the hypervisor, at most 0.04% of intervals longer than 1.5 refresh periods). The hypervisor mode was validated only with cold boots of one Android image on one AMD PC; snapshots, guest reboots, injected NMIs and x2APIC were not tested.

The Windows download contains the desktop client only. The source kit adds gate R to the published engine patch and recognizes `whpx_apic_hv` in `engine_manifest.py`.
