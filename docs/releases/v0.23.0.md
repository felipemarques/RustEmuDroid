# RustEmuDroid v0.23.0

Windows x64 users can select a separately built performance engine for an Android profile. Open **Settings → Runtime, image, and profile → Performance engine (experimental)**, choose a folder that contains `rustemudroid-engine.json` next to its `sdk` subfolder with **Choose performance engine…**, then save and restart Android. Installed games, accounts and saves stay on the profile's Android disk. **Remove performance engine** switches the profile back to the regular engine. A profile uses either this engine or the Vulkan memory cache engine from v0.22.0, not both. [Build and stage the engine](../../experiments/whpx-clock/README.md#4-build-the-performance-engine)

The manifest names the engine version and build and the SHA-256 of the launcher, QEMU core and gfxstream renderer, plus optional helper files. The desktop checks every digest at each start. If a file is missing, changed or unreadable, or the profile does not use an SDK image with host or automatic GPU, it reports the reason and starts Android with the default engine. A folder the current user cannot read is reported as "No permission to read" with its path.

Settings shows a switch only for the options the manifest lists:

| Switch | Default | Engine setting |
|---|---|---|
| CPU virtualization tuning | On | Synchronized TSC, local APIC fast path and KVM paravirtual end of interrupt. The guest then identifies its hypervisor as KVM. |
| Cached Vulkan memory | On | Cached host-visible and mappable device-local Vulkan memory |
| Graphics commands through shared memory | On | `hw.gltransport=asg` with a 3000 µs consumer spin, about one host core while a game renders |
| Compose the screen with Vulkan | On | `VulkanNativeSwapchain` |
| Dedicated cores for Android | On | Each vCPU on its own physical core, away from core 0. Offered only when the PC has more physical cores than the profile's vCPUs plus two. |
| Reduce Android kernel protections | Off | Appends `mitigations=off init_on_alloc=0 transparent_hugepage=always` to the profile's own kernel parameters, with a warning in Settings |

All emulator features of a start are passed in one `-feature` argument, for example `VulkanNativeSwapchain,-VulkanAllocateDeviceMemoryOnly` when the Radeon 780M option is also on. Every inherited `RUSTEMUDROID_QA_*` variable is removed before the engine starts.

The transport and kernel options change the profile's `config.ini`. The desktop records the original lines first in `rustemudroid-performance.json` next to it and restores them byte for byte when the option is turned off, the engine is removed or a start falls back to the default engine. Kernel parameters already in the profile are kept and not repeated; an edit to that line while the option is on is replaced by the recorded original at restore. If `config.ini` is read-only, not UTF-8 or cannot be written, or the record is damaged, the message names the file and nothing is changed.

Android starts without waiting for the engine's confirmation. The desktop keeps reading the engine log for up to 10 seconds after boot, and once more when the VM exits, then posts one status line with the confirmed options. Engines that write some lines only at exit are reported as "Not confirmed in the engine log (this does not mean it is off; older engines write some lines only at exit)", followed by the options and the log path.

A separate per-profile option, **Windows best performance power mode while Android runs**, activates the Best performance power mode while Android is open and restores the previous mode when the last VM closes. The power plan itself is not changed. It is skipped on battery. If the PC switches to battery before Android closes, the previous mode is restored at the next start on AC power. It is off by default.

The performance engine is also available from PowerShell with the default preset, without kernel parameters. It writes `hw.gltransport` to the profile's `config.ini`, keeps about one host core busy while a game renders and makes Android report KVM:

```powershell
.\rustemudroid.exe --state-dir 'D:\Android\MyProfile' boot --gpu host --performance-engine 'D:\Android\PerformanceEngine'
```

Preference entries for the performance engine and the power mode that cannot be read are skipped; the rest of `launcher.json`, including the selected profile, still loads.

**Going back to v0.22.0.** v0.22.0 ignores the new preferences and the record file. If you downgrade while a profile still uses the performance engine, its `config.ini` keeps `hw.gltransport=asg`, and `kernel.parameters=…` when that option was on. Before downgrading, choose **Remove performance engine** in Settings, save and start Android once so the original lines are restored, or delete those lines by hand.

On the Windows test PC (RTX 5070 Ti, official Android 17 Google Play image, SuperTuxKart 1.5 Black Forest at High, Vulkan Mailbox uncapped), these engine settings measured **356 game FPS** with the Windows Balanced power mode and **375** with Best performance, compared with 164–176 for the stock engine. Kemu measured 325 and 358 and BlueStacks 376 and 396 in the same session on an otherwise idle desktop; other programs running in the background lowered the result to 309–350 FPS per lap. A test operator applied those settings around the v0.22.0 client. In a later daytime series with other programs running and the published-source engine build, the v0.23.0 client applying the same settings from its own preferences measured 341.8 FPS against 342.5 for the operator path. The engine log showed the same options in all four boots, and `config.ini` was back to its original bytes afterwards. [Client and operator paths](../../docs/performance-history.md#client-and-operator-paths) On the integrated Radeon 780M at 60 Hz, Cipó Livre went from 58.61 and 57.38 to 59.93 and 59.89 presentations per second in two scenes, with intervals longer than 1.5 refresh periods falling from 4.86% and 9.15% to 0.17% and 0.08%. [Conditions, recipe and limits](../../docs/performance-history.md#performance-engine-in-uncapped-mailbox)

The Windows download contains the desktop client only. The engine is built from the published source kit, which adds the `performance` build variant, the `engine_manifest.py` tool that writes `rustemudroid-engine.json` after checking each capability in the binaries, and a fix for folders staged from an elevated prompt, which the normal launcher could not read.
