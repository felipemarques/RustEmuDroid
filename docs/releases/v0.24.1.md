# RustEmuDroid v0.24.1

On Linux with an AMD graphics card (the amdgpu driver with RADV) and the **Host GPU** mode, games no longer end the session with `Engine exited (signal: 6 (SIGABRT))`, and Unity games no longer stop with `Vulkan - Out of memory!` on cards whose firmware exposes a small memory window. The client prepares this by itself. Windows, other graphics vendors on Linux, the engine, the Android images and existing profiles are unchanged. [AMD graphics on Linux](../../docs/linux-runtime.md#amd-graphics-on-bare-metal-linux)

On Linux the **Automatic** GPU mode currently ends in the emulator's software renderer, because the client starts the engine with `-no-window`. The AMD handling matters with the **Host GPU** mode. This release does not change that.

**What was wrong.** When the host Vulkan device is from AMD on Linux, the stock Android Emulator turns on two memory features by itself. `VulkanAllocateDeviceMemoryOnly` leaves Android only the part of the card's memory that the processor can reach. With "Above 4G Decoding" / "Resizable BAR" off in the firmware that window is 256 MB, and Unity games ran out of it while loading. `VulkanAllocateHostMemory` hands ordinary process memory to the graphics driver. Each time the engine started a helper program (adb, `chattr`), the driver could not get that memory back within its one-second limit, rejected the next commands (`radv/amdgpu: The CS has been rejected, see dmesg for more information (-16).`) and the engine aborted with `Encountered device lost.` The same rejection was also seen once with no helper program involved; its cause was not identified.

**What changes on Linux with an AMD card.**

- The client carries a small library ([source](../../native/linux/userptr_guard.c), built with the client), writes it to `~/.local/share/RustEmuDroid/lib/` and adds it to the engine's `LD_PRELOAD`. An `LD_PRELOAD` you already use is kept. If the library can not be written, Android starts without it and the boot details say why. The library defends the driver's memory in two ways:
  - It keeps that memory out of the start of the engine's helper programs, so starting one no longer takes it away from the driver.
  - When the driver still rejects a batch of drawing commands because it could not get that memory in time, the library makes the memory available again and sends the same commands again, for up to 30 seconds. The rejected commands had not been submitted, so sending them again repeats nothing.

  If the driver keeps rejecting for 30 seconds, the engine still ends, and the client then says that the graphics driver lost the device.
- The client then chooses how much of the card's memory Android sees:
  - **Full size**, when the processor-visible window is smaller than the video memory: the emulator's options stay, and the library reports the whole video memory to the engine as processor visible, so the memory Android can map has its real size.
  - **Stock**, when the window already covers the video memory or the sizes can not be read: the emulator's options are left alone.

  A third mode, **all types** (`-feature -VulkanAllocateDeviceMemoryOnly`, which also gives Android the memory types outside the card), is never chosen automatically, because it froze Android on the one kernel it was measured on. `VulkanAllocateHostMemory` is never changed.
- **Technical details** shows one line with what the client prepared before the engine started, for example `AMD graphics on Linux: video memory protection prepared; with the host GPU, Android sees the whole 8192 MB instead of the 256 MB window.`
- When the graphics driver does lose the device, the failure reads `The graphics driver lost the device and the engine exited (…)` with the log path, in place of the bare signal.
- When the engine prints `kvm run failed`, Android is frozen although the engine is still running. The client now stops that VM and explains the cause instead of showing nothing.
- `doctor` prints one line of advice when the card's window is smaller than its memory and the kernel is older than 6.13.

**Measured.** Everything was measured on one PC and one kernel: Radeon RX 580 8 GB with a 256 MB window, RADV / Mesa 25.2.8, Linux 6.8, Android Emulator 37.3.10 and the official Android 17 Google Play image. With the library loaded and the options applied by hand around the stock engine, before the library resent rejected commands:

| Game | Stock | All types | Full size |
|---|---|---|---|
| Xtreme Rally (Unity 6 URP) | Out of memory | Works, 10 minute race | Works, 10 minute race, peak video memory 3980 MB |
| FPS WW2 (Unity URP) | Out of memory | Works | Works |
| Godot third-person demo | Works | Works | Works |
| Godot 4.7 game | Menu for 150 s without a freeze, not played further | Android frozen after 5 s, `kvm run failed Bad address` | Android frozen after 20 s |
| Unreal Engine 5 game | The game closes itself (engine assertion), Android keeps running | Android frozen after 18 s | The game closes itself, Android keeps running |

None of these hand-applied runs lost the graphics device. Without the library, with all types, the device was lost 13–14 s into the race, twice out of two. In full size, the sequence that first showed the fault (the Unreal Engine game twice, then a 240 s race) and a 600 s race both ran without a graphics error.

The first run through the client did lose the device, once: 87 s into a race in full size with the Host GPU mode, with the library active and, at that time, only its first defence (`The CS has been rejected (-16)`, then `Encountered device lost`). The client showed the new "graphics driver lost the device" message. The cause of that one event was not identified. On this path the engine starts its helper programs only during boot, before the driver holds any of that memory, so it was not a helper program. The PC was under heavy memory activity at the time, which is a coincidence in time and not a proof. Two later runs on the same path, of 420 s and 900 s, did not repeat it. The second defence was added after that event. With the final library:

- Rejections provoked on purpose (stock engine started with `-qt-hide-window`, all types, the first defence switched off for the test): the driver rejected 8 batches of commands in a 150 s race and every one was accepted when sent again, six after one more attempt in 9–33 ms and two after two more attempts in about 1050 ms. No device was lost. The same configuration without the library lost the device 13–14 s into the race, 2 of 2.
- Through the final client (`boot --headless --gpu host`, lab profile): a 300 s race without a graphics error. The library was installed under the user data folder, the preload and the variable were present in the engine process, and nothing had to be sent again. <!-- soak: result of the 30 minute race through the final client -->
- All types forced through the final client with the Godot 4.7 game: `kvm run failed Bad address` 9 s after the game started. The client stopped the VM and showed its explanation with "256 MB of 8192 MB, kernel 6.8".
- The Linux build of the final tree: `cargo fmt` clean, release build with `--features ui`, 157 tests passed, 12 ignored.

**Expected, not measured.** On Linux 6.8, KVM can not map the driver's system-memory pages into the guest; that is what freezes Android with `error: kvm run failed Bad address`, and the Godot 4.7 game still does so in full size. Going by the kernel and driver sources, enabling **Above 4G Decoding** and **Resizable BAR** in the firmware (BIOS/UEFI), or using Linux 6.13 or newer, should remove these freezes, and all types should work on Linux 6.13 or newer. Nobody has run either, so the client only suggests them and does not choose all types by itself. Other AMD cards, integrated AMD graphics and computers with two AMD cards were not tested.

For diagnosis, set `RUSTEMUDROID_AMD_LINUX` before starting the client: `off` starts the engine as before, and `stock`, `full-size` or `all-types` loads the library and forces that memory mode.

A source build on Linux now also compiles the library with `cc` (or the compiler named by `CC`). The Linux download contains the desktop client only, with the library inside it.
