# RustEmuDroid v0.25.0

On Windows, the panel now reads Android's screen from a memory region it shares with the engine, instead of receiving the pixels of every frame inside the gRPC messages of `streamScreenshot`. Nothing has to be turned on, and no temporary file is used. The client falls back to the previous path by itself when the engine refuses the region, does not write into it, shows no picture through it or a read fails, and says why in the boot details. On Linux the same path exists and stays off unless it is asked for, because it has never run against a real engine there. The engine, the Android images, existing profiles, the settings and the BlueStacks preview are unchanged. [Measurement of November 27](../../benchmarks/stk-1.5/windows-rtx-mailbox-shared-memory-panel-bluestacks.md)

**Where it was verified.** On the Windows test PC with the separately built performance engine, with the Android Emulator that first-time setup installs and with the Vulkan cache engine. With the last two, on a disposable Android 17 profile, the client reported shared memory for the whole session, and the panel kept changing while Android's Settings list scrolled, after an 8 second still screen, after resizing the window to 800 × 450 and after turning the screen and back. It has not been verified with Kemu's engine; there, as with any engine that does not provide shared memory, the client continues with the previous path by itself.

**How it works.** The client creates the region and names it in its request. The engine writes each frame into it and then sends a message that only announces the frame. The client then copies the newest announced frame from the region.

- **Windows.** The region is a named memory mapping backed by the paging file. It exists only while it is in use, so nothing is written to a disk and nothing is left behind.
- **Linux.** The region is a file in `/dev/shm` that only your user can open. The client creates and fills it, so a full `/dev/shm` fails in the client and not inside the engine, and files left by clients that no longer run are removed at the next start. This code is exercised by the offline tests only: it has **never run against a real engine on Linux**, which is why it is off there by default.

A region is as large as one full frame of the profile's screen, about 5.8 MB at 1600 × 900.

**The variable.** `RUSTEMUDROID_VIDEO_TRANSPORT` is read when the client starts.

| Value | Windows | Linux |
|---|---|---|
| not set | Shared memory | Frames inside the messages |
| `shared` | Shared memory | Shared memory |
| `inline` | Frames inside the messages, as in v0.24 | Frames inside the messages, as in v0.24 |

**Falling back by itself.** When shared memory does not work, the client continues with the frames inside the messages, as in v0.24, until Android is started again. That happens when the engine refuses the region or answers the request with an error of its own, sends the pixels inside the messages anyway, announces frames without writing them into the region or shows no picture through it, and when the region can not be created or read or a frame does not fit in it. Shared memory is not tried when the profile's screen can change size, as with resizable and foldable device definitions.

**What you see.** One line names the path each time it changes, in the three languages, in **Settings → Launcher output** and under **Technical details** on the session screen:

- `Panel video: memory shared with the engine.`
- `Panel video: frames inside the control channel; shared memory was not used because …`, followed by the reason, for example that the variable turned it off, that on this system it has not been tested with the engine yet (Linux without the variable), that the engine refused the memory region, with the engine's own code and message, or that the engine announced frames without writing them into the region.

The reason shown when the engine closes the video stream is now in the three languages too.

**Limits.**

- **A torn frame is possible.** The engine does not synchronise its writes with a reader: it can begin writing the next frame while the client is still copying the current one, and nothing in the region says so. The client looks for a newer frame after every copy and copies again when there is one, which does not catch every case. Such a picture is drawn torn, and right after a rotation one frame can be drawn with the shape of the previous one. The next frame replaces it. Screenshots and recordings are made from the same frames.
- **If the picture looks wrong**, start the client with `RUSTEMUDROID_VIDEO_TRANSPORT=inline`. That is the display path of v0.24.
- **A leak in the engine, not fixed here.** When the engine can open the region but can not map it, which needs a frame larger than the region, it never closes its handle, and that memory stays until the engine exits. A region is as large as the largest frame of its screen, so this is not expected, and the client can not close the engine's handle.
- **Linux.** Not run against a real engine yet. `RUSTEMUDROID_VIDEO_TRANSPORT=shared` turns it on for a test.

**Measured.** One alternated session on November 27, 2026, 10:23–11:07, on the Windows test PC (Ryzen 9 8945HS, GeForce RTX 5070 Ti): SuperTuxKart 1.5, Black Forest replay at High, Vulkan with the game's VSync off (Mailbox, uncapped), game FPS from the game's own frame report, the Windows Best performance power mode only, two timed laps per boot after one warm-up lap.

| Arm | Laps (FPS) | Mean |
|---|---|---:|
| BlueStacks 5 Pie64 | 342.7 · 375.3, 374.9 · 371.1, 356.2 · 346.0 | 361.0 |
| RustEmuDroid, shared memory, 800 × 450 panel | 408.5 · 404.0, 386.5 · 391.6 | 397.6 |
| RustEmuDroid, shared memory, default 1040 × 585 panel | 401.7 · 415.0, 372.6 · 414.6 | 401.0 |
| RustEmuDroid, frames inside the messages (the v0.24 path), 800 × 450 panel | 367.4 · 389.8, 369.7 · 362.7 | 372.4 |

What has to be said about these figures:

- **The client was not the published v0.25.0 executable.** It was a build made before the release at commit `a7efd99`, the first two feature commits of this version on top of the v0.24.0 source. A lab harness started it on a disposable Android 17 Google Play profile with the separately built performance engine and set the engine's environment. The feature commits made after that build and the release itself were not timed in this session. The arm with the frames inside the messages is the same build with `RUSTEMUDROID_VIDEO_TRANSPORT=inline`.
- **This series does not establish a lead over BlueStacks.** BlueStacks measured 361.0 here against 419.3 in the series of November 26 on the same PC and workload, about 14% lower, and the cause is not known. The desktop was in use, and each BlueStacks step began 25 seconds after the owner's everyday Android VM had been booted, which the BlueStacks operator then closed for its timed boot. RustEmuDroid's arm with the frames inside the messages was 2–5% below its figures of November 26 (372.4 against 379.1–393.6). The series shows RustEmuDroid ahead in this session, and shared memory 6.8% ahead of the frames inside the messages at the same panel size in the same session, with four laps per arm and one lap of the slower arm inside the range of the faster one. A repeat on an idle desktop, in both power modes and with Kemu, is pending.
- The client ran with **Fit video frames to the window** on, which is off by default. Full-size frames were not measured, nor the default panel with the frames inside the messages.
- The harness captured the client window during every lap: 89–96% of the panel's pixels changed between consecutive captures in every timed lap, so the picture was live.
- Kemu was not measured. The three BlueStacks steps completed their laps and then ended with exit status 1, as in the earlier series: closing the player through its exit dialog failed, and the operator ended the player and restored the instance's preferences.

**Tests.** The offline tests run the panel's video worker against a stand-in for the engine that writes the regions from its own thread while the client copies. They cover a writer that never pauses, a rotation in the middle of a copy, and each reason for falling back with its text in the three languages.

The Windows and Linux downloads contain the desktop client only. The performance engine used in the verification and in the measurement is built separately from the published source kit and is not part of the download.
