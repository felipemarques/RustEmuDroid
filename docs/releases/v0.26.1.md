# RustEmuDroid v0.26.1

When the engine stops with `exit code: 0xc0000094` (a division by zero), the failure now explains what happened instead of showing the bare code, in Brazilian Portuguese, US English and Spanish from Spain, and every failure of a running Android session now names the app that was open when it happened. The panel, the engine, the Android images and existing profiles are unchanged.

**What was reported.** On v0.26.0, opening a game with the cache engine ended the session with `Engine exited (exit code: 0xc0000094)`. v0.26.0 had just made the engine's own surface the default picture of the panel, so that change was the first suspect.

**What was wrong.** The panel was not involved. On a disposable profile with the same engine, Android image, game and graphics card, the engine stopped 18–26 seconds after the game started, with the same code, in every run:

| Engine | Panel | Runs | Result |
|---|---|---:|---|
| Cache engine | Engine's surface (the v0.26.0 default) | 7 (2 on v0.26.0, 5 on v0.26.1) | Engine stopped, `0xc0000094` |
| Cache engine | Always copy the frames | 3 (1 on v0.26.0, 2 on v0.26.1) | Engine stopped, `0xc0000094` |
| Default engine | Always copy the frames | 1 | Engine stopped, `0xc0000094` |

A debugger attached only to the test engine recorded the fault at the same place in every run: inside the graphics card's driver, which divided by zero while the engine asked it how much memory a texture needs. The texture used a compressed format the graphics card does not support. The engine handles such formats itself, but it asks the driver about the texture before it switches to that handling. The project's game testing notes record the same ending on v0.4.0.

**What changes.**

- When the engine ends with `0xC0000094` and its log does not explain more (a lost graphics device, a failed virtualization), the failure reads `The engine stopped on a division by zero inside the graphics card's driver (0xC0000094). This is known to happen with some games that use a compressed texture format the graphics card does not support. Changing the emulator's settings does not avoid it; keep that game closed`, followed by the exit code and the log path as before. Other exit codes keep the plain message.
- A failure of a running session ends with `App open when it happened: <package>`, the last app other than Home reported in the foreground. The client asks Android for it every 5 seconds while Home is ready (every second, as before, while the control mappings or the Android FPS counter need it) and keeps the last answer when a later question fails, as it does once the engine has stopped.
- The failure box on the start screen shows up to 8 rows instead of 6, so the explanation, the log path and the app fit without opening **Technical details**.

**Tried, not a workaround.** Asking the game for the other graphics API avoids the crash, but the game then refuses to run because it needs a newer version of that API than the engine offers. Other graphics driver choices for the game end it inside Android's processor translation as it starts, before it uses the graphics card. A real fix belongs in the engine: answering that question without the driver for the formats the engine handles itself. That needs a rebuilt engine and is not part of this release.

**Checks.** `cargo fmt --check` clean; `cargo test --locked --release --features ui`: 314 passed, 0 failed, 28 ignored; `cargo build --locked --release --features ui`: `rustemudroid.exe` SHA-256 `9f596f6b4d49f71b4522f92c8e4f5fbbd81c160c01f278b788f96f776ba72815`, `rustemudroid 0.26.1`. Builds of v0.26.1 opened the game on the same disposable profile seven times (the engine's surface and copied frames, in the three languages) and showed the explanation with the app's package; the final text was checked with this build in Portuguese, where the explanation, the log path and the app fit in the box. A game that runs normally was still running in the engine's surface after 40 seconds.
