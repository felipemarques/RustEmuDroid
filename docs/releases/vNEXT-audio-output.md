# RustEmuDroid vNEXT (draft): audio output

**Settings → Sound → Audio output** chooses where Android's sound plays. The first entry, **System default**, is selected for new and existing preferences and shows the device the system uses now. With it the client changes nothing in the engine: on Windows the engine's audio back end opens the Windows wave mapper and on Linux it opens a PulseAudio stream without a sink, so Android follows the system default output, also when you change it while Android runs. The other entries are the computer's active output devices by their friendly names. A choice is saved in `launcher.json` (`hardware.audio_output` and its display name) and applies after saving and restarting Android. If the saved device is not connected at startup, Android uses the system default and the launcher output says which device was missing.

How a chosen device is reached:

- **Windows.** The stock engine has no device option. When a device other than the default is chosen, the engine starts with `-no-audio` and the RustEmuDroid window plays the engine's `streamAudio` gRPC stream (48 kHz stereo, 16-bit) through that device with WASAPI in shared mode. The engine sends about 100 packets of 10 ms per second while Android plays, and nothing while Android's audio is idle. In a live session the packets were 0.2 ms old on arrival and the client held 20–52 ms of audio (queue plus device buffer, about 30–40 ms on average) before the device's own output latency. The engine's clock ran slightly slower than the device's (about 1 ms per second); the player repeats or skips a single frame per write when its buffer leaves 30–70 ms, so it neither runs dry nor grows, and it trims back to 40 ms above 160 ms. The end-to-end delay from Android to the speaker has not been measured. The host microphone is unaffected in practice: the engine already sends silence to Android's microphone unless host audio input is allowed, and `-no-audio` also turns that input off. If the device disappears during the session, the sound moves to the current system default and the launcher output says so. Only the RustEmuDroid window can do this; `boot` without the window keeps the system default and says so.
- **Linux.** The client sets `QEMU_PA_SINK` to the chosen PulseAudio sink (PipeWire through pipewire-pulse works the same way) and lists the sinks with `pactl`. **System default** removes an inherited `QEMU_PA_SINK`. While the embedded panel still starts the engine with `-no-window`, the headless engine binary has no sound at all (its PulseAudio library is a stub); the launcher output says so, and the choice takes effect once the panel runs the engine with a hidden window.

Command line: `rustemudroid audio-outputs` lists the devices with their IDs and marks the system default; `boot --audio-output <ID or name>` chooses one.

Tested: unit tests for device matching, the boot plan (environment, `-no-audio`, messages, fallback), `pactl` parsing, preference round trip and labels, the gRPC request encoding and the playback queue. On the Windows test PC, the device list matched the system's five active outputs, and an opt-in test played a 1 kHz tone through the player on VB-Audio "CABLE Input" (not the default device) and recorded it back from "CABLE Output" at the expected level and frequency. 

Live sessions on the Windows test PC (stock Emulator 37.3.10, official Android 17 Google Play image, a disposable profile, Android ringing for an incoming call from its own emulator console):

- **System default:** the engine (`qemu-system-x86_64.exe`) owned the only RustEmuDroid audio session, on the system default output, with a session peak of 0.16; nothing reached the virtual cable.
- **VB-Audio "CABLE Input" chosen:** the engine ran with `-no-audio` and owned no audio session on any output; the client owned the session on CABLE Input (peak 0.16) and the ringtone was recorded from "CABLE Output" for 6 seconds (peak 5238 of 32767).
- **A saved device that does not exist:** the launcher output said "The saved audio output “Missing Test Speaker” is not connected. Android uses the system default output.", the engine ran without `-no-audio` and the client played nothing.

Not tested: any Linux desktop, unplugging the chosen device during a session, and changing the system default during a session.
